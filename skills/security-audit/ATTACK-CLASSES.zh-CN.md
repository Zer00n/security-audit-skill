# 攻击类

> 本文为英文原文 [`ATTACK-CLASSES.md`](ATTACK-CLASSES.md) 的简体中文译本。

#### 攻击类 — 根据第 1 阶段选择与拆分

选择与应用类型相关的攻击类。并非每个类适用于每个代码库。下列清单是起点；从第 1 阶段增加应用特定类，并按 subsystem 拆分大型代码库。将工作框定为发现、验证、修复与优先级排序漏洞。验证限于源码审查与有界本地夹具；不要开发 payload 链、对实时服务测试可用性，或在共享环境中采取行动。

仅当源码证据与有界验证确立完整边界与有意义结果时使用 `confirmed`。当特定部署、提供商、平台、身份或运行时事实不可用时使用 `needs_validation`；陈述缺失事实与解决它的安全所有者观察或本地检查。

> **原生 / 二进制 / 内核目标**（C/C++/Rust-unsafe、内核模块、解析器与解码器、FFI、并发运行时、二进制加载器、JIT、固件）：使用 [MEMORY-SAFETY-AND-BINARY.md](MEMORY-SAFETY-AND-BINARY.md) 中的内存安全、整数/ABI、并发、二进制加载器与特权接口类。
>
> **AI / LLM / Agent 目标**（聊天机器人、RAG、持久记忆、工具调用 Agent、MCP 服务器/客户端、提示组装或模型控制动作）：使用 [AI-AND-LLM.md](AI-AND-LLM.md) 中的上下文、记忆投毒、动作绑定、工具 schema、MCP 身份与输出类。
>
> **HTTP、Web 与身份目标**（普通 Web 应用、API、反向代理、CDN、网关、自定义 HTTP 解析器、会话、CSRF、JWT、OAuth/OIDC、SAML、MFA、通行密钥、账户恢复/关联、API 密钥或 mTLS）：使用 [WEB-PROTOCOL-AND-AUTH.md](WEB-PROTOCOL-AND-AUTH.md)。
>
> **客户端与浏览器目标**（SPA、浏览器扩展、嵌入式 webview、service worker、浏览器存储、跨窗口消息、CORS、WebSocket 或 DOM 渲染）：使用 [CLIENT-SIDE.md](CLIENT-SIDE.md)。
>
> **供应链与发布目标**（依赖解析、生成输入、CI、发布/签名/晋升、更新、插件或扩展）：使用 [SUPPLY-CHAIN-AND-RELEASE.md](SUPPLY-CHAIN-AND-RELEASE.md)。
>
> **云与部署目标**（IAM、基础设施即代码、容器/Kubernetes、服务网格、无服务器/边缘、入口、提供商事件或运行时配置）：使用 [CLOUD-AND-DEPLOYMENT.md](CLOUD-AND-DEPLOYMENT.md)。
>
> **协议、RPC 与消息目标**（gRPC、GraphQL 传输、Protobuf/Cap'n Proto/Thrift、自定义协议、队列、broker、pub/sub、webhook 或流式 RPC）：使用 [PROTOCOLS-RPC-AND-MESSAGING.md](PROTOCOLS-RPC-AND-MESSAGING.md)。
>
> **资源耗尽与可用性目标**（不受信任的工作可消耗共享 CPU、内存、磁盘、连接、worker、队列、配额或运营方拥有的支出）：使用 [RESOURCE-EXHAUSTION-AND-AVAILABILITY.md](RESOURCE-EXHAUSTION-AND-AVAILABILITY.md)。
>
> **数据隔离与生命周期目标**（多租户存储、缓存/搜索、对象链接、分析、导出/备份、迁移、删除、保留或恢复）：使用 [DATA-ISOLATION-AND-LIFECYCLE.md](DATA-ISOLATION-AND-LIFECYCLE.md)。
>
> **桌面、移动与本地 IPC 目标**（原生应用、深度链接、webview 桥、导出组件、特权 helper、本地 daemon、Unix socket/XPC/Binder/D-Bus）：使用 [DESKTOP-MOBILE-AND-LOCAL-IPC.md](DESKTOP-MOBILE-AND-LOCAL-IPC.md)。

**Injection**（subagent_type: `general`）
从入口点到危险汇点追踪不受信任输入。「危险汇点」取决于应用：
- Web 应用：SQL 查询、HTML 输出、shell 命令、模板引擎、文件路径、HTTP 重定向、反序列化
- 库：任何未经验证处理调用方提供数据的函数 — 缓冲区操作、解析器、格式字符串
- CLI 工具：shell 命令构造、文件路径处理、环境变量插值
- 服务：查询构造、消息序列化、日志注入、LDAP/XPATH 查询
- 客户端（浏览器/JS）：DOM XSS、原型污染、`postMessage`/源信任及其他浏览器侧类 — 在选择时由 [CLIENT-SIDE.md](CLIENT-SIDE.md) companion 块覆盖

不要停在明显直接路径。寻找间接注入：数据安全存储，然后由不同代码检索并用于危险上下文。寻找通过字段名、键、头与元数据的注入 — 不只是值。寻找进入二级系统（日志、缓存、搜索索引、分析）的注入。

**Access control**（subagent_type: `general`）
验证调用方不能做超出其权威的事。超越检查权限检查是否存在 — 验证它们通过*正确*机制检查*正确*资源的*正确*权限：
- 是否存在检查不同（更弱）权限到达同一状态变更的路径？
- 请求体中的字段能否覆盖权限系统意图限制的内容？
- 是否存在门控认证但忘记授权的端点？
- 同一资源是否有多个访问路径且检查不一致？
- 批量/批处理/导出/导入操作如何 — 它们是否强制每项权限？

对复杂访问模型，拆分为认证绕过 vs 授权逻辑的独立 Agent。

**Resource and file handling**（subagent_type: `general`）
- 路径遍历（在预期目录外读/写）— 包括通过符号链接、编码序列与空字节
- SSRF（使应用获取攻击者控制的 URL）— 包括通过重定向、DNS 重绑定与 URL 解析器差异
- 不安全反序列化、归档解压（zip slip）、临时文件处理
- 内存安全（若适用）：缓冲区溢出、use-after-free、整数溢出
- 文件操作上的竞态条件（检查与使用之间的 TOCTOU）

**Cryptography and secrets**（subagent_type: `general`）
- 安全关键值（令牌、密钥、nonce）的弱随机性
- 硬编码密钥、日志中的密钥、错误消息、URL 或客户端可见响应
- 破损的密钥派生、缺失 HMAC 验证、nonce 重用
- 密钥比较上的时序侧信道
- 加密原语误用（ECB 模式、未认证加密、静态 IV 等）
- 加密操作失败时发生什么？错误路径是否回退到无加密？

**Business logic**（subagent_type: `general`）
手工狩猎逻辑错误：标准扫描器找不到它们，且它们产出高影响 finding。对每个主要工作流：
- **状态机违反**：能否跳过步骤？后退？到达无效状态？重放已完成流程会怎样？部分失败呢 — 若 3 步中的第 2 步失败，第 1 步是否回滚？
- **有业务影响的竞态条件**：产生无效状态的并发操作（双花、双批、丢失更新）。聚焦非原子检查后行动的操作。
- **数值/数量操纵**：负值、零值、溢出、精度损失、字符串与数字间的类型强制。
- **访问边界违反**：不是「权限检查是否存在」而是「它对业务规则是否是正确检查？」一个操作的输入能否绕过对同一效果在不同操作上强制的限制？
- **隐式信任假设**：来自存储、配置、其他组件或插件的数据因「我们在入口验证过」而被假设安全。若不同代码路径写入它呢？
- **基于时间的逻辑**：过期检查、调度、速率窗口、时钟偏差。精确边界时刻发生什么？组件间时区差异呢？
- **默认与回退行为**：配置缺失时的安全态势？功能开关关闭时？依赖不可用时？系统处于迁移中时？

**Feature abuse and data leakage**（subagent_type: `general`）
合法功能被用于非预期目的。寻找设计中的缺陷，不只是代码中的：
- **导出/备份作为渗出**：低权限用户能否触发包含超出其访问级别数据的导出、快照或备份？他们能否导出其他用户数据？导出是否包含已删除/草稿/私有内容？本应修剪的修订历史？
- **导入/恢复作为注入**：导入能否覆盖现有数据？能否创建绕过正常验证的记录？能否向用户无写权限的集合注入内容？它是否尊重与 UI 相同的权限模型？
- **搜索/过滤/排序作为 oracle**：搜索查询能否揭示用户不能直接访问的内容是否存在？过滤参数能否让用户探测他们不应知道的状态、角色或字段？按隐藏字段排序能否通过结果顺序揭示其值？
- **通过副作用枚举**：错误消息在「不存在」与「无访问」之间是否不同？响应时间？响应大小？HTTP 状态码？能否通过密码重置、邀请或注册流程枚举用户？
- **预览/草稿/预发布泄漏**：预览令牌是限定单项还是解锁更广访问？草稿内容能否通过搜索、RSS、站点地图或 API 列表端点发现？缓存头能否使 CDN 公开提供私有内容？
- **通知/webhook 作为 SSRF**：用户能否设置服务器获取的通知 URL、webhook URL 或回调 URL？是否针对内部网络验证？重定向后呢？

**Chained vulnerabilities and trust boundaries**（subagent_type: `general`）
单独允许或受控的行为，在另一组件或生命周期步骤依赖更强保证时可成为漏洞：
- **多步边界失败**：映射低权限主体可读、写、调用与保留的内容，然后仅将具体输出连接到后续信任决策。确认每个先决条件，不要假设下游效果。
- **跨组件信任缺口**：组件 A 验证输入并传给组件 B。比较 A 产生的确切保证与 B 假设的内容，包括截断、类型强制、规范化、租户范围与插件/扩展访问。
- **二阶使用**：存储时安全的数据在后续上下文中可能变危险。字段名变为 JSON 路径，slug 变为文件路径，转义文本进入原始渲染，或存储字符串变为 URL、正则、模板或策略表达式。
- **范围与能力增长**：令牌、API 密钥、插件、OAuth、MCP 或 AI 能力在委托、刷新、缓存、角色变更或组合后变广。命名结果主体不应拥有的具体操作。
- **时序与排序**：审查设置、迁移、软删除、撤销/缓存过期、检查/使用与验证/消费窗口。在报告前确认过时状态被接受。
- **回滚与恢复**：取消删除、恢复、修订回滚与取消必须应用当前所有权、验证与授权。确认恢复了哪个无效状态。

**Wildcard**（subagent_type: `general`）
不给你类别。在已分配的标准类之外寻找漏洞。

阅读看起来无聊或与安全无关的代码。跟随不完整、实验性、兼容性与回退功能，但保留与其他每个类相同的具体边界与验证要求。

使用这些起点，但不要限于它们：
- 代码库中最奇怪的代码是什么？它为何存在？若被滥用会发生什么？
- 是否有半成品、实验性或外挂式功能？它们因审查最少而安全最弱。
- 若以前端绝不会用的方式使用 API 会怎样？UI 约束用户，但 API 不约束。哪些 API 调用可能但客户端从不发出？
- 是否有隐藏或未文档化的端点、参数、头或功能？查看路由注册、中间件与配置中文档没有的内容。
- 混用设计上不一起工作的功能会怎样？本地化 + 预览 + 缓存。导入 + 插件 + webhook。OAuth + 冒充 + API 密钥。
- Git 历史中有什么有趣内容？回退的安全修复、注释掉的认证检查、曾提交后删除的密钥（仍在历史中）。
- 哪些有效账户动作影响其他用户、共享完整性、可用性或运营方拥有的成本？围绕这些动作验证遏制、配额、授权与恢复。
- 哪些操作不可逆或需要提升确认？将授权与批准绑定到最终主体、动作与资源。
- 代码对环境做了哪些假设？数据库是本地的、时钟准确、DNS 可信、文件系统区分大小写？
- 查看测试文件 — 它们**没有**测试什么？比较开发者想到的边界情况（有测试）与未想到的（无测试）。

在分配范围内追求异常，直到不变量确定。若某事看起来奇怪，读到你能陈述它是否安全。若函数有解释为何安全的注释，验证该解释。若变量名为 `temp`、`hack` 或 `legacy`，仔细阅读。

**Obvious things**（subagent_type: `general`）
其他 Agent 狩猎微妙缺陷。本 Agent 检查因人人假设别人已检查而容易忽略的基本暴露：
- 源码中是否有硬编码密码、API 密钥、令牌或密钥？（grep `password`、`secret`、`apikey`、`token`、`Bearer`、`-----BEGIN`、常见默认密码）
- 是否有引用安全的 TODO/FIXME/HACK/XXX 注释？（`TODO: add auth`、`FIXME: validate input`、`HACK: skip permission check`）
- 调试模式 / 开发模式是否正确门控？能否通过环境变量、查询参数或头在生产启用？
- 是否有在生产中有效的测试/示例/种子凭据？
- 是否有未保护的 `/debug`、`/admin`、`/test`、`/status`、`/health`、`/metrics`、`/env`、`/.env`、`/config` 端点？
- 仓库中是否签入任何 `.env`、`.env.local`、`credentials.json`、`*.pem`、`*.key` 文件？
- `.gitignore` 是否真正覆盖密钥、上传与本地配置？
- 依赖是否固定？依赖树中是否有已知 CVE？（检查 lockfile）
- 是否有带动态输入的 `eval()`、`exec()`、`child_process`、`Function()`、`vm.runInContext`、`import()`？
- CORS 头是否设为 `*` 或过度宽松？`Access-Control-Allow-Credentials` 是否与通配源组合？
- Cookie 是否缺少 `HttpOnly`、`Secure` 或 `SameSite` 属性？
- 是否有开放重定向？（名为 `redirect`、`return`、`next`、`url`、`goto`、`continue` 且未经验证进入重定向的参数）
- 是否强制 TLS？是否有仅 HTTP 端点？
- 生产错误响应是否返回堆栈跟踪、内部路径或 SQL 错误？

本 Agent 不需要有创意。它需要彻底且字面。检查每一项。报告每个结果。

**重要**：对本 Agent 报告的任何 finding，必须验证完整代码路径，不只是表面外观。若 Cookie 缺少 `HttpOnly`，检查 Cookie 是否包含安全敏感数据以及 JS 是否按设计需要读取它。若错误消息包含字段名，检查该字段是否实际填入敏感数据。标志不是 finding — 在报告前追踪影响。
