# 安全审计技能：最佳实践手册

本手册面向在仓库中使用 `security-audit` 技能的实践者与编排者。它不是各文档的机械摘录，而是把 `SKILL.md`、侦察/狩猎/验证与报告阶段，以及各 attack-class companion 中已经写明的约束，整理成可执行的操作指南。

相关中文译本见根目录 [`README.zh-CN.md`](../README.zh-CN.md) 与 `skills/security-audit/*.zh-CN.md`。英文原文保留为同名文件。

---

## 1. 概述：技能解决什么问题、适用场景

**解决什么问题**

- 把编码 Agent 编排成**防御性、源码优先**的安全审计员。
- 用确定性 `coverage-ledger.json` 驱动覆盖，避免「看起来审过了」的空话。
- 用对抗式验证（发现者 ≠ 核验者）压低假阳性。
- 产出结构化 `findings.json` 与目标中性报告，便于所有者修复与再审计。

**适用场景**

| 场景 | 模式 | 说明 |
|------|------|------|
| 明确要求审计 / pen-test / 全面评审 / 报告产物 | Full audit | 跑满六阶段并写产物 |
| 安全问题、聚焦评审、分流、方法论 | Guidance | 只用相关片段；不自动建输出目录 |
| 同一仓库的增量再审计 | Full audit + prior runs | 继承 ledger/findings，优先缺口与变更源码 |
| 子集路径、单 subsystem、单 companion 域、两 ref 间 diff | Scoped full audit | 范围外记为 `out_of_scope`，自称部分覆盖 |

**不解决什么**

- 不代替生产渗透测试、红队对共享环境的探测。
- 不自动把「缺少最佳实践 / 缺纵深防御层」升格为漏洞。
- 在缺少 OS 强制沙箱时，不执行目标代码；线索保留为 `needs_validation`。

## 2. 设计原则速查

1. **只确认已确立的边界失败**  
   有源码依据但关键事实在源码/沙箱外的线索 → `needs_validation`（带精确未决事实），不要猜部署行为后标 `confirmed`。

2. **对抗式验证**  
   发现候选的 hunter 不得核验自己的 finding。第 3/5 阶段用新 verifier；实质性替换再换独立 verifier。

3. **严重级别需要影响**  
   可能性 × 影响；总体严重级别**不得超过**已证明影响。`needs_validation` **无** severity。

4. **纵深防御缺口 ≠ 漏洞**  
   Layer A 已挡住攻击时，缺少 Layer B 记为 hardening note，不是 finding。

5. **多次运行提升覆盖**  
   单次运行通常不完整；技能设计为累加。测试中单次大约只发现重复运行合计漏洞的一半——规划上要按多轮覆盖，而不是「跑完一次就穷尽」。

附加不变量（贯穿全文）：

- 候选必须能说清：较低信任主体、接受的输入/动作、应生效的控制、被穿越边界、受影响主体/资源、可观察结果。
- 本地证据止于**最小边界结果**；禁止扩大伤害、实时探测、付费配额消耗。

## 3. 六阶段工作流最佳实践

### 阶段总览

| 阶段 | 目标 | 主要输入 | 主要输出 |
|------|------|----------|----------|
| 1 侦察 | 映射架构与种子 ledger | 目标源码、既有 ledger/findings、预算/profile | `run-metadata.json`、`architecture.md`、`coverage-ledger.json` |
| 2 覆盖驱动狩猎 | 按单元狩猎并关闭覆盖 | Ledger `planned` 单元、攻击类块 | Hunter JSON、更新后的 ledger、候选 |
| 3 候选验证 | 对抗式证伪/确认 | 去重后的候选 | 每 fingerprint 的判定记录 |
| 4 结构化输出 | 写入并校验 findings | 独立判定记录 | `findings.json`（两校验器通过） |
| 5 独立记录核验 | 新鲜视角核验最终记录 | `findings.json` | 核验通过或替换；必要时 incomplete |
| 6 目标中性报告 | 从最终记录派生散文 | findings + ledger + hardening | `REPORT.md` / `FINDINGS-DETAIL.md` / `NEEDS-VALIDATION.md` |

终态只有两种：(a) 第 6 阶段产物齐备且两校验器通过；(b) `run_status: "incomplete"` 带精确原因并在报告披露缺口。**禁止阶段中途静默停止。**

### 3.1 侦察

**目标**：只读映射产品、主体、入口面、本地可执行边界与 companion 选择；种子确定性覆盖单元。

**常见坑**

- 接触已部署端点 / 外部 IdP / 云 API（禁止）。
- 仅因语言名出现就加载 companion（应按「When to use this file」边界选择）。
- 把架构散文当成覆盖证据（覆盖只认 ledger）。
- 预算门失败仍启动侦察 Agent。

**检查清单**

- [ ] `run-metadata.json` 含 `profile`、`scope_paths`、`budget`、`execution_policy`、`source_ref`
- [ ] 预算门通过后再派 1a–1d（及必要聚焦侦察）
- [ ] `architecture.md` ≤ ~1000 词；assignment 块地图在 ledger 单元内
- [ ] 种子后运行 `validate-coverage-ledger.cjs`
- [ ] 既有运行的继承规则已按 `SKILL.md` / `RECONNAISSANCE.md` 执行

### 3.2 覆盖驱动狩猎

**目标**：按优先级分配 `planned` 单元；hunter 返回结构化结果；post-wave / final-clean critic 找缺口。

**常见坑**

- 因 Agent 数量限制静默漏分配（应显式 `deferred`）。
- 只发 companion 文件名而不复制 verbatim 块。
- 把 crash 夸大为 RCE、把同主体行为当成提权。
- 在沙箱不完整时仍执行目标代码。
- 用波次上限暗示「覆盖完成」。

**检查清单**

- [ ] 分配前：单元 → `in_progress`，创建 `scratch/` + parent 拥有 `artifacts/`
- [ ] 提示含：role、architecture、单元地图、verbatim 攻击类块、排除原因、方法/提升/门、排除的 prior confirmed、schema 分支
- [ ] 每单元结果映射到恰好一个 `coverage_id`；更新后校验 ledger
- [ ] Critic 预留在狩猎配额之前；`quick` 仅一波 hunter + 一最终 critic
- [ ] `uncovered` 进入下一波新单元，而非被吞掉

### 3.3 候选验证

**目标**：新 verifier 尝试证伪；输出 `confirmed` / `needs_validation` / `rejected`。

**常见坑**

- Verifier 看到其他 verifier 结论。
- 把投机想法停放在 `needs_validation`。
- 未验证候选写入 `findings.json`（预算不足时应留在 ledger 且 run incomplete）。

**检查清单**

- [ ] 每候选独立 verifier + 独立 scratch
- [ ] 重读所有引用源码；可安全复现则独立复现
- [ ] Fingerprint 跨状态稳定；畸形结果丢弃重跑
- [ ] 携带 prior confirmed 同样走当前验证路径

### 3.4 结构化输出

**目标**：按 fingerprint 排序写入 `findings.json`，严格分枝字段，跑两校验器。

**检查清单**

- [ ] 写入前重读 `report-schema.json`（`additionalProperties: false`）
- [ ] `confirmed` / `needs_validation` / `rejected` 字段集互不串用
- [ ] `node validate-findings.cjs` 与 `validate-coverage-ledger.cjs` 均通过

### 3.5 独立记录核验

**目标**：核验结构化记录本身（非 hunter 文稿）。`quick` 可合并进第 3 阶段；其他 profile 保持两遍分离。

**常见坑**

- 只核验 `confirmed`，放过误导性 `needs_validation`。
- 实质性替换未经新独立 verifier 即定稿。

**检查清单**

- [ ] 每个保留的 confirmed / needs_validation 有独立核验
- [ ] 实质性替换 → 新 verifier；无法核验 → 移出 findings，ledger 保留候选，`incomplete`
- [ ] 每次替换后重跑两校验器

### 3.6 目标中性报告

**目标**：散文不得改判定/严重级别/阻塞项/影响；无实时探测说明。

**检查清单**

- [ ] 首节诚实披露 profile、预算、部分覆盖、incomplete 原因
- [ ] Confirmed 表与 Needs Validation 表分开；后者无 severity
- [ ] Rejected 不当 finding 宣传
- [ ] 复现说明使用目标原生接口（未必是 HTTP）

## 4. coverage-ledger 与 findings 判定

### Ledger 单元状态（语义摘要）

| status | 含义 | 证据要求（摘要） |
|--------|------|------------------|
| `planned` | 待分配 | 无 owner、证据空 |
| `in_progress` | 已分配 | 有规范 owner，证据空 |
| `covered` | 已审查无候选 | owner + 非空 paths/checks |
| `candidate` | 产出候选 | owner + 证据 + fingerprint |
| `blocked` | 部分审查受阻 | owner + 部分证据 + unresolved |
| `deferred` / `out_of_scope` / `not_applicable` | 未做或范围外 | null owner、空证据、非空原因 |

`attempts` 仅追加归档；再分配时活动证据清空，新 owner，不把归档检查拷回活动态。

### Findings 三判定

| verdict | 何时 | 有无 severity | 要点 |
|---------|------|---------------|------|
| `confirmed` | 完整源码追踪 + 有界观察结果 + 有意义跨边界影响 | 有 | 含 `root_cause`、`execution`、`remediation` 等 |
| `needs_validation` | 源码假设成立但决定性事实在本地不可见 | **无** | 精确 `blockers` + 适用 `validation_plan` |
| `rejected` | 源码/本地行为/可见控制证伪 | 无 | 保留以免重复假说 |

**判定口诀**

- 缺最佳实践、无受影响主体 → hardening / 排除，不是 finding。  
- 源码已证伪 → `rejected`，不是 `needs_validation`。  
- 未验证候选 → 只在 ledger，不进 `findings.json`。

## 5. 攻击面与攻击类选择

**原则**：按侦察发现的**信任敏感边界**选 companion，不按「用了某语言/依赖」选。

| 目标特征 | 加载 |
|----------|------|
| 通用注入、访问控制、业务逻辑、功能滥用等 | `ATTACK-CLASSES.md`（几乎总是） |
| C/C++/unsafe/FFI/内核/解析器/JIT | + `MEMORY-SAFETY-AND-BINARY.md` |
| LLM / RAG / Agent / MCP / 提示组装 | + `AI-AND-LLM.md` |
| HTTP 分帧、缓存、会话、JWT/OAuth/SAML/MFA | + `WEB-PROTOCOL-AND-AUTH.md` |
| SPA / 扩展 / webview / DOM / postMessage | + `CLIENT-SIDE.md` |
| 依赖、CI、签名发布、更新、插件 | + `SUPPLY-CHAIN-AND-RELEASE.md` |
| IAM、IaC、K8s、无服务器、入口 | + `CLOUD-AND-DEPLOYMENT.md` |
| gRPC/队列/broker/webhook/流式 RPC | + `PROTOCOLS-RPC-AND-MESSAGING.md` |
| 共享资源耗尽、配额、可用性 | + `RESOURCE-EXHAUSTION-AND-AVAILABILITY.md` |
| 多租户数据、导出备份、删除恢复 | + `DATA-ISOLATION-AND-LIFECYCLE.md` |
| 原生应用、深度链接、本地 IPC、helper | + `DESKTOP-MOBILE-AND-LOCAL-IPC.md` |

Hunter 提示须**逐字复制**所选 ordinary 块与 companion 的 `Core discipline` / 所选小节 / `Universal moves` / `Validation rules`；排除块须写明源码事实原因。

## 6. 沙箱与安全执行要求

目标可控执行（构建、测试、进程、浏览器、模拟器、fuzzer、夹具）**必须**在 OS 强制沙箱中，且同时满足：

1. **无外部网络**（仅隔离 loopback 用于本地夹具）  
2. **空环境 + allowlist**（scratch 本地 `HOME`/临时目录/缓存）  
3. **只读目标与工具链**；进程仅写分配的 `scratch/`  
4. **低资源与挂钟限制**（CPU/内存/进程/文件大小/磁盘/时间）

**写隔离要点**

- 共享产物仅 parent 写。  
- Agent 只写自己的 `scratch/`；`artifacts/` 由受信任 parent 侧按 no-follow、描述符遍历、普通文件、大小上限流程提升。  
- 禁止 `/tmp` 或主机家目录作可写回退。  
- 不安装/拉取依赖；只用本地已有工具。

任一控制不可强制 → **不执行**目标代码；以精确缺失能力记 `needs_validation`。

## 7. 多次审计与增量覆盖

1. 规划前读所有兼容的既有 `coverage-ledger.json` 与 `findings.json`。  
2. **同源未变** confirmed：带入候选集、同 fingerprint、链到 `planned` 单元、hunter 排除该根因、走当前最终核验。  
3. **源码已变** confirmed：新建 revalidation 单元；不排除根因；不假设旧判定仍成立。  
4. 既有 `needs_validation` / `deferred` / `blocked` / `out_of_scope` / 变更单元 → **当前工作**，永不当抑制键。  
5. 既有 `rejected` 仅抑制未变失败主张，不抑制单元覆盖。  
6. 既有 `quick`/scoped 绝不隐含「其余没问题」。  
7. Profile：`quick`（粗单元、一波）、`standard`（书面流程）、`deep`（细单元、critic 至 clean、双遍核验）。

预算：先预留侦察基线、critic、验证，再分配 hunter；无法预留则 `deferred` 或整 run `incomplete`，诚实披露。

## 8. 反模式清单

1. 检查清单偏差当漏洞。  
2. 无可达边界违反的纵深防御建议当 finding。  
3. 有界本地证据不足时做实时/共享环境测试。  
4. 猜测源码中不存在的提供商/代理/浏览器/身份/部署行为。  
5. 同主体权威或自我影响当成跨边界结果。  
6. 报告强于观察到的效果（如 crash → RCE）。  
7. 纯散文 hunter 结果，无法去重/核验。  
8. 重复报告携带的同源 prior confirmed，或用其锚定狩猎。  
9. 给 `needs_validation` 分配 severity。  
10. 独立核验前写报告，或散文与 JSON 不一致。  
11. 静默超出用户严格预算，或把未验证候选塞进 findings。  
12. 用 Agent 数量或波次上限冒充覆盖完成。

## 9. 报告产物与读者沟通

| 产物 | 读者用途 |
|------|----------|
| `REPORT.md` | 执行摘要、态势、confirmed 表、needs-validation 表、hardening、覆盖摘要 |
| `FINDINGS-DETAIL.md` | medium+ confirmed 的完整追踪与目标中性复现 |
| `NEEDS-VALIDATION.md` | 未决线索：追踪、阻塞项、本地/所有者观察计划（无 severity） |
| `findings.json` | 机器可读真相源；散文不得改判定 |
| `coverage-ledger.json` | 覆盖主张的机器可读真相源 |

沟通要点：

- 部分运行（quick / scoped / 预算受限 / incomplete）必须在报告首节说清楚。  
- Needs validation 是**待办线索**，不是「低置信漏洞」。  
- 复现使用目标原生接口；不要默认 HTTP 或要求目标没有的实时环境。  
- 干净运行可以零 confirmed——如实说明剩余覆盖/验证限制，不要发明 LOW finding。

## 10. 快速开始与推荐运行方式

### 安装

```bash
npx skills add https://github.com/cloudflare/security-audit-skill \
  --skill security-audit
```

用户级：加 `--global`。

### 触发示例

```
security audit this codebase
```

```
find security vulnerabilities in ./src
```

```
do a security review, output to ~/audits/my-project
```

未指定输出目录时，完整审计默认：`~/security-audit-skill/<repo-name>/run-<N>`。仅当目录被 VCS 忽略且用户明确选择时，才写入目标仓库内。

### 推荐运行方式

1. **首次接触大仓库**：`quick` 或 scoped 摸清入口面与 companion 选择，接受「部分覆盖」叙事。  
2. **常规审计**：`standard`，预留 critic + 验证预算后再开 hunter。  
3. **高利害 / 合规**：`deep`，细 ledger，critic 至 clean，候选验证与最终核验分离。  
4. **再审计**：带上先前 `coverage-ledger.json` 与 `findings.json`，优先变更源码与未决线索。  
5. **无完整沙箱**：坚持源码审查 + `needs_validation` 计划；不要「差不多能跑」就执行目标代码。  
6. **每次 ledger / findings 变更后**立刻跑对应校验器；失败先修结构再继续分配。

### 最小质量门（跑完自问）

- 每个 confirmed 能否一句话说清边界与已证明影响？  
- 每个 needs_validation 是否有**唯一**精确阻塞项与可执行计划？  
- Ledger 是否能解释「审了什么 / 没审什么」？  
- 报告是否与 `findings.json` 一致且目标中性？
